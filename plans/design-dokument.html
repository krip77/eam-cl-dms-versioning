Versionshanterad DMS-checklista

Ny lotbaserad Z-FM som ersätter EAM_CL_CREATE_DMS_LOT och, istället för att skapa ett nytt dokument per checklista, skapar en ny version av ett befintligt dokument kopplat till det tekniska objektet (EQ/FL) + ordern + inspektionsloten, identifierat via provplan i klassificeringen. Äldre version arkiveras. Checklistans PDF lagras helt in-memory via CV-API:t (CVAPI_DOC_CREATE / CVAPI_DOC_CHECKIN) – samma mekanism som SAP-standardens create_dms_from_spool, utan temp-fil/SAPFTPA.

Bakgrund och återanvändning

Båda standard-FM:erna (eam_cl_create_dms_lot, eam_cl_create_dms_order) gör i grunden: (1) läser config via cl_eam_cl_cu=>otpl_read → ls_otpl (innehåller DOCTYPE, STORAGECATEGORY, WORKPAPER), (2) genererar spool via SUBMIT EAM_CL_PRINT, (3) PERFORM create_dms_from_spool ... ls_drad som skapar dokumentet och objektlänken. Idag länkas dokumentet bara till lot (QALS) eller order (PMAUFK):

Vi bygger en ny FM ZVFI_FG_E_AM_D_CR_DMS_LOT_VER med samma interface som lot-FM:en (drop-in i QM follow-up action). Steg 3 byggs på samma in-memory-mekanism som standardens create_dms_from_spool – spool → PDF (xstring) → DRAO-tabell → CVAPI_DOC_CREATE (pf_content_provide='TBL'), helt utan temp-fil. Skillnaden mot standard: vi länkar mot tekniskt objekt + order + inspektionslot, klassificerar dokumentet (provplan) och hanterar versionering.

Flöde

flowchart TD
  Start[Start follow-up action] --> Guards["Guard: läs lot/order, otpl_read, validera workpaper=EAM_CL_PRINT"]
  Guards -->|deaktiverad / ej config| Stop[Return]
  Guards --> Doctype["Doctype = gc_doctype (annars otpl) · status ur TDWS (FRKNZ / DOSAR='A')"]
  Doctype --> Tech["Tekniskt objekt ur i_qals: LS_EQUNR → EQUI, annars LS_TPLNR → IFLOT"]
  Tech --> Spool["EAM_CL_PRINT-spool → CONVERT_OTFSPOOLJOB_2_PDF (xstring) → DRAO-tabell"]
  Spool --> Lock["ENQUEUE serie (valfritt)"]
  Lock --> Search["Sök: DRAD doctype + objektlänk EQ/FL + klass-match D_CL_PLNTY/PLNNR/PLNAL/WERKS/MATNR"]
  Search -->|ej hittad| Create["CVAPI_DOC_CREATE: DIR + 3 länkar + PDF in-memory, ingen status → icke-releasad"]
  Create --> Rel1["COMMIT → BAPI_OBJCL_CHANGE (5 chars) → sätt Released → COMMIT"]
  Search -->|hittad| NewVrs["CVAPI_DOC_CREATE (doknr + nästa dokvr): ny version + 3 länkar + PDF in-memory, ingen status"]
  NewVrs --> Rel2["COMMIT → BAPI_OBJCL_CHANGE (5 chars) → sätt Released → COMMIT"]
  Rel2 --> Archive["Arkivera föregående version → COMMIT"]
  Rel1 --> Log["E_PROTOCOL + add_msg_to_log + COMMIT (ej i_test)"]
  Archive --> Log

Implementation

  • Interface: spegla EAM_CL_CREATE_DMS_LOT exakt (I_QALS, I_QAVE, I_QAPO, I_NO_LOG_SAVE, I_TEST, I_DIALOG, E_SUBRC, E_PROTOCOL).
  • Guard clauses: läs i_maintorderinspectionlot (skip om mainchecklistisdeactivated), läs aufk, otpl_read, validera t390/EAM_CL_PRINT och hämta formulärtitel.
  • Status från customizing: determine_statuses läser released/archived ur TDWS per doctype – released = FRKNZ = 'X', archived = status typ DOSAR = 'A'. Konstanterna gc_status_released/gc_status_archived är bara fallback.
  • Tekniskt objekt (per lot!): läs objektet direkt från i_qals – EQUI om LS_EQUNR finns, annars IFLOT från LS_TPLNR. En order kan ha en objektlista med en lot per objekt, så objektet måste tas per lot, inte från orderhuvudet.
  • Spool → PDF (in-memory): återanvänd EXPORT/SUBMIT EAM_CL_PRINT/IMPORT-blocket; konvertera spoolen med CONVERT_OTFSPOOLJOB_2_PDF och pdf_destination='X' så PDF:en kommer direkt som xstring (bin_file) – inte via tline-tabell. Dela sedan xstringen i en binär DRAO-tabell med SCMS_XSTRING_TO_BINARY. löser 0-byte-buggen
  • Sök befintligt dokument: SELECT FROM drad WHERE dokar = <doctype> AND dokob = <EQUI/IFLOT> AND objky = <tekn objekt>; för träffarna läs klassificering (klasstyp 017, klass D_CL, objekttabell DRAW) via BAPI_OBJCL_GETDETAIL och matcha alla nyckel-egenskaper var för sig (ingen konkatenering): D_CL_PLNTY/D_CL_PLNNR/D_CL_PLNAL/D_CL_WERKS/D_CL_MATNR. Match kräver att samtliga stämmer; välj högsta DOKVR.
  • Gren – ej hittad (första version): CVAPI_DOC_CREATE skapar DIR:en med originalet i ett svep – doctype, beskrivning, objektlänkar (EQUI/IFLOT + PMAUFK + QALS) och PDF-innehåll (pt_content = DRAO). Ingen status sätts → dokumentet landar i doktypens icke-releasade initialstatus. Därefter COMMIT, sätt de 5 klass-egenskaperna med BAPI_OBJCL_CHANGE, och sätt Released explicit → COMMIT.
  • Gren – hittad (ny version): samma mekanism som första versionen – CVAPI_DOC_CREATE med ps_draw-doknr = befintligt dokument och ps_draw-dokvr = nästa version skapar den nya versionen med originalet i ett svep (3 länkar + PDF in-memory, ingen status). Sen COMMIT, klassificera (5 chars), sätt Released explicit, och arkivera föregående version med BAPI_DOCUMENT_CHANGE2. Ingen CREATENEWVRS2 – fällan där en ny version hamnar i releasad/låst status och blockerar incheckning av originalet kan därmed inte uppstå.
  • Samtidighet (valfritt låsobjekt): lock_series gör ENQUEUE_<lockobjekt> (nyckelfält SCOPE, CHAR50, läge E) på serien med _wait = 'X'; släpps vid COMMIT WORK. Saknas objektet degraderar FM:en med varning. gc_lock_object = space stänger av.
  • Idempotens (valfritt): om gc_char_lot är satt lagras PRUEFLOS på versionen och samma lot skapar ingen dubblettversion vid omkörning.
  • Objektlänkar: tekniskt objekt (EQ/FL) + order (PMAUFK) + inspektionslot (QALS). På ny version säkerställs aktuell lots länkar via BAPI_DOCUMENT_GETDETAIL2/CHANGE2 (idempotent skyddsnät); lots ackumuleras som historik.
  • Status (status type L / semi-lock): den releasade statusen (RE) är statustyp L så att klassificeringen kan sättas efter att dokumentet skapats. Statustyp L kan inte vara initialstatus → systemet auto-releasar inte; programmet sätter Released explicit efter att originalet är committat (annars meddelande 26269). Gammal version → Archived. Värden ur TDWS. Detta är en staged-commit-modell (skapa → COMMIT → klassificera/release → COMMIT).
  • Logg/commit: bygg E_PROTOCOL (meddelanden), anropa cl_eam_cl_msg_tool=>add_msg_to_log, COMMIT WORK om inte I_TEST. Använd i_test som testrun i BAPI:erna (ingen commit).

BAPI:er och funktionsmoduler som används

Lagringen är helt in-memory via CV-API:t – PDF:en flyttas aldrig till en filyta. Nedan vad varje anrop gör och var i flödet det körs.

  • cl_eam_cl_cu=>otpl_read – läser shop paper-/utskriftsconfig för ordertypen (DOCTYPE, STORAGECATEGORY, WORKPAPER).
  • SYSTEM_UUID_C_CREATE + SUBMIT EAM_CL_PRINT – genererar checklistans spool; UUID:t kopplar utskriftsparametrarna via minnet (id_iprt_options).
  • CONVERT_OTFSPOOLJOB_2_PDF (pdf_destination='X') – konverterar OTF-spoolen till PDF direkt som xstring.
  • SCMS_XSTRING_TO_BINARY – delar PDF-xstringen i en binär DRAO-tabell som CV-API:t läser in-memory (pf_content_provide='TBL').
  • CVAPI_DOC_CREATE – skapar dokumentet med originalet i ett anrop, utan status. Första version: nytt doknr. Ny version: samma anrop med ps_draw-doknr = befintligt dokument + ps_draw-dokvr = nästa version. Returnerar dok-nyckeln. Detta är den enda vägen som skapar dokument/versioner.
  • CVAPI_DOC_CHECKIN – (reserverad, används ej i scenario 1/2) in-memory-incheckning av original på en befintlig version; vägen för det framtida "byt fil på samma version"-scenariot.
  • BAPI_DOCUMENT_GETACTVERSION – hämtar aktiv (högsta) version inför sökmatchning och versionering.
  • BAPI_OBJCL_GETDETAIL / BAPI_OBJCL_CHANGE – läser/sätter de 5 klassificerings­egenskaperna (klass D_CL, klasstyp 017) som identifierar dokumentserien (provplan). Används vid sökmatchning, vid sättning på nytt dokument och vid återställning på ny version.
  • BAPI_DOCUMENT_GETDETAIL2 – läser befintliga objektlänkar för idempotent länk-säkring.
  • BAPI_DOCUMENT_CHANGE2 – sätter dokumentstatus (Released på aktuell version, Archived på föregående) och lägger till saknade objektlänkar.
  • ENQUEUE_<lockobjekt> (valfritt) – samtidighetslås på serien; släpps vid COMMIT WORK.
  • cl_eam_cl_msg_tool=>add_msg_to_log – skriver applikationsloggen (E_PROTOCOL + BAPI-returer).
  • COM_SE_SPOOL_DISPLAY (valfritt, I_DIALOG='X') – visar spoolen direkt för felsökning.

Framåtblick: för scenariot "samma lot körs om med ändrad fil" är planen CVAPI_DOC_CHECKOUT_VIEW + CVAPI_DOC_CHECKIN på samma version, med content versions aktiverat för full spårbarhet. (Inte byggt än.)

Konstanter (bekräftade mot systemets customizing)

  • gc_doctype = dedikerad dokumenttyp för den versionshanterade checklistan (space = använd shop paper-doktypen från otpl_read). Statusnätet måste ha en icke-releasad initialstatus och RE som statustyp L.
  • gc_classtype = '017' (Document Management), klass gc_class = 'D_CL'.
  • Nyckel-egenskaper – en char per fält (klass D_CL, ren läs/skriv utan parsning):
    • gc_char_plnty = 'D_CL_PLNTY' (CHAR1) ← QALS-PLNTY (provplanstyp)
    • gc_char_plnnr = 'D_CL_PLNNR' (CHAR8) ← QALS-PLNNR (provplansgrupp)
    • gc_char_plnal = 'D_CL_PLNAL' (CHAR2) ← QALS-PLNAL (gruppräknare)
    • gc_char_werk = 'D_CL_WERKS' (CHAR4) ← QALS-WERK (verk)
    • gc_char_matnr = 'D_CL_MATNR' (CHAR18) ← QALS-MATNR (material)
  • gc_char_lot = valfri egenskap för idempotens (lagrar PRUEFLOS); space = av.
  • gc_status_released = 'FR', gc_status_archived = 'AR' är fallback – statusarna läses i runtime ur TDWS (released FRKNZ='X', archived DOSAR='A').
  • gc_lock_object = valfritt kundlåsobjekt för samtidighet (space = av).
  • gc_storage_cat = lagringskategori för originalet (space = DMS-default).

Designval (förvalda – säg till om du vill ändra)

  • Objekt per lot: objektet tas från i_qals (LS_EQUNR/LS_TPLNR). Är båda ifyllda (utrustning installerad på funktionsplats) väljs EQUI, annars IFLOT.
  • Inget tekniskt objekt på loten: versionshantering är inte möjlig → logga varning och avbryt (e_subrc = 4).
  • Orderlänkar ackumuleras: vi säkerställer enbart aktuell order + tekniskt objekt på nya versionen; ev. medkopierade äldre orderlänkar lämnas kvar som historik.
  • Material som egen char (CHAR18): mycket långa (extended) materialnummer trunkeras i egenskapen; med korta materialnummer är detta oproblematiskt och matchningen är konsekvent.

Förbättringar / sånt som kan ha missats

  • Idempotens (klart, valfritt): PRUEFLOS kan lagras i gc_char_lot så att samma lots omkörning inte skapar dubblettversion. Av som default.
  • Samtidighet/lås (klart, valfritt): ENQUEUE på serien (tekn objekt + nyckel-chars) via valfritt kundlåsobjekt, släpps vid COMMIT WORK. Degraderar med varning om låsobjektet saknas.
  • Statusnätverk (klart): statusarna läses dynamiskt ur TDWS (released = FRKNZ='X', archived = status typ DOSAR='A'); konstanterna är fallback. Övergången Released → Archived måste fortfarande vara tillåten i statusnätet.
  • Content versions (backlog): när ett protokoll redan finns för loten ska den existerande versionen uppdateras med ny PDF i stället för att hoppas över, så justeringar fångas. Förutsätter content versions på doktypen; kräver check-out av gammalt original + ersättning, och jämförelse av filstorlek (ev. hash) för att undvika onödiga content-instanser. Avvaktar tills grundflödet är verifierat.
  • Flera matchande dokument: tie-breaker = högsta version/senaste; överväg att logga om fler än ett "serie"-dokument hittas (datafel).
  • Behörighet: C_DRAW_*-kontroller hanteras av BAPI:erna; testa med körande användares behörighet.
